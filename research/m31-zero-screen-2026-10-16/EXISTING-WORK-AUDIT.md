## M8/M9: what the existing browser work actually computes

M8’s [WGSL kernel](https://github.com/denghanjie/drone-swarm-aerodynamics-public/blob/1336f5c416875a9651f92b58b2ed06649f25b04e/outputs/milestone-08-source/kernel.wgsl) uses one invocation per vehicle, workgroup size 64, and a state of five `vec4f` values: position, velocity, quaternion, angular velocity and four nominal motor forces. That is 20 packed floats/80 bytes carrying 17 physical states. RK4 normalizes the quaternion after each step. The model includes gravity, thrust/torque, gyroscopic terms and motor lag, using mass 0.027 kg, gravity 9.81, inertia `(1.4e-5,1.4e-5,2.17e-5)`, arm coordinate 0.028 m and motor lag 0.04 s. It contains no interacting aerodynamic field or receiver root solver.

M8 executes 50 steps at dt=0.01 s under fixed commands in one dispatch. Both CPU and GPU start from identical Float32-quantized inputs; CPU then uses JS binary64 and GPU uses f32. Frozen component tolerances were position 1e-3 m, velocity 1e-3 m/s, quaternion 1e-4, angular velocity 1e-3 and motor force 1e-5 N. All four sizes passed historically. At N=5,000, reported medians were 1,000.50 ms CPU and 1.20 ms GPU plus transfers; maximum position-component difference was 0.0106 mm.

Those large ratios compare an allocation-heavy CPU reference with 50 GPU steps per dispatch. Timing uses `performance.now`, upload/dispatch/mapAsync synchronization/readback, one warmup and three repeats; it excludes allocation/compilation, rendering and control, and uses no GPU timestamp queries. The selected run paused rendering; an earlier rendering-active run was retained. Neither ratio establishes interacting force throughput or application FPS. Reuse [M8 app.js](https://github.com/denghanjie/drone-swarm-aerodynamics-public/blob/1336f5c416875a9651f92b58b2ed06649f25b04e/outputs/milestone-08-source/app.js), its protocol, report and loopback receiver as prior buffer/dispatch/readback and evidence-handling examples.

M9 reuses the shader with one step per dispatch at 100 Hz. CPU clearance scheduling/control and swept-neighbor checking remain outside the GPU. Each step repacks/uploads states and commands and reads the whole state back. The one-second queue has fixed 0.6 m spacing, grows to roughly 600 m at N=5,000, has airflow off and mostly waiting vehicles. It is not a dense interacting flock or a completed passage. Three repeats followed ten warmup steps at N=50 per backend. All sizes passed final-position tolerance 1 mm and crossing/stop/close-pair agreement.

At N=5,000, [M9 reports](https://github.com/denghanjie/drone-swarm-aerodynamics-public/blob/1336f5c416875a9651f92b58b2ed06649f25b04e/outputs/milestone-09-report.md) 2,969.9 ms CPU versus 1,334.6 ms hybrid per simulated second, real-time factor 0.75. Independent component medians are approximately 475 ms control, 462 ms mechanics/transfers and 401 ms checking. At N=50 CPU is faster. Its swept AABB grid inserts expanded segment bounds into all intersected cells and checks candidate pairs once; 100 deterministic random comparisons plus an explicit crossing passed against exhaustive checking. This collision structure is reusable engineering, not an already implemented GPU wake-neighbor structure.

Separate instanced Three.js/WebGL rendering reported 0.80 ms median at N=5,000, with five warmups, 30 frames and synchronous `gl.finish`. The long queue/light pixel workload and separate execution preclude adding this number to compute timings and calling the sum verified interactive FPS. Useful paths are `outputs/milestone-09-source/{app.js,neighbors.js,scheduler.js,check-neighbors.mjs}`, the protocol and verification records. No GPU-resident controller or neighbor grid was found.

## Later DOT: exact and approximate CPU field work already attempted

[Spatial pruning](https://github.com/denghanjie/drone-swarm-aerodynamics-public/blob/1336f5c416875a9651f92b58b2ed06649f25b04e/research/campaign-spatial-pruning/REPORT.md) preserves the M28 fixed isolated-hover-strength compact mean wake: 2.5 m downstream support, three half-widths radially, 3 m center search and the original 1.5 m grid cells. It prepares axes/world rotor points, retains all four receiving rotors, and uses the same receiver law and load mapping. An independent near-domain guard precedes omission. A center-envelope upper bound with separated extrema/fade bounds supports ascending-source greedy inflow budgets 0.002/0.01/0.04 m/s; matched zero control pays the bound cost but drops only exact-zero support. Force/moment screens were 0.005 weight and 0.0075 weight×arm. Source SHA256: `1d9e1afcf9983b900034b7b586c4ffd02ec4b3242c467f8e684fbdda1850d562`.

Completed evidence spans 4,848 snapshots, N=16/50/100/200, four seeds, three families and 101 times; 1,330,776 receiver comparisons had no bound/domain/nonfinite failures and zero matched-control differences. Maximum observed force/moment errors were 0.000343458918 N and 0.000006408602 Nm. However, **0/36** pruning timing comparisons met both ≥10% saving and paired 95% upper ratio <1. Zero-control versus legacy gains of 1.53–1.95× also include scalar/allocation/support changes and cannot be attributed to positive omission. Eight one-second N=16 Boids records completed; refresh sensitivity was much larger than pruning perturbation. The retained v0 bound omitted fades and omitted no positive terms; its correction preceded held-out use. No GPU computation occurred.

[Exact efficiency](https://github.com/denghanjie/drone-swarm-aerodynamics-public/blob/1336f5c416875a9651f92b58b2ed06649f25b04e/research/campaign-exact-efficiency/REPORT.md) directly addresses avoiding that positive-bound overhead. Original source checkpoint is `c024dfc27b9e6b7cd5b39132164d1339cb95b12f`; `src/exact-aero.cjs` SHA256 is `6111d7a70a7ca60ed7404889042e4f0ad61c852794289fc6f5e95d67070c9189`.

Its five comparators are unchanged legacy M28; previous-zero (still computes positive bounds); **lean** scalar geometry/kernel without pair bounds; **support** adding conservative exact-zero center-envelope checks to lean, without the positive tail; and **reuse** adding refreshed internal Float64Array geometry/Uint8 scratch with fresh caller-owned outputs. It preserves component grouping/initial-zero dot arithmetic, rotor-major traversal and ascending source IDs, first-error behavior, a global tilt gate, and distinctions between zero-support pairs needing a near-domain guard and those conservatively outside it. This is JS binary64, not f32.

The accepted API requires nonempty arrays of 17 finite state entries, quaternion norm tolerance 1e-10 and position components within ±1e6 m. A retained translation around 3e14 m falsely culled a 0.001587065203100887 m/s term; the revised bounded domain includes a 128 epsilon×1e6 ≈2.84217e-8 m envelope margin. A legacy grid hang at 1e20 m remains documented. These restrictions and arithmetic choices matter when reusing code. `loads` consumes current nominal motor inputs at indices 13–16 and original nominal yaw; current static M31 queries instead prescribe f0=mg/4=0.0662175 N and yaw zero.

Exact-field gates were inflow 1e-12, force 1e-12 N and moment 1e-13 Nm; timing required median ratio ≤0.9 and paired 95% upper ratio <1. Development seeds were 4301/4302 and held-out seeds 4391/4392. All 151 primary cases had zero maximum differences. Independent checks had 78 valid fixtures bitwise equal, seven matching domain failures, 45 transform checks, 33 ownership checks and 39 explicit API rejection assertions.

Lean was selected. It passed 8/12 primary N=100/200 gates versus previous-zero, so scaling stopped before N=500. Independent nonzero cases passed 12/12 versus legacy but only **3/12** versus previous-zero; the corrected 3/12 count must supersede historical 4/12 wording (four met only the median threshold). Fourteen Boids records completed and eight matched pairs had exact state/held-field hashes. Primary N=16 pipeline ratio versus previous-zero was 0.911; independent ratio was 0.960, 95% interval [0.936,1.018]. Neither supports a stable 10% whole-pipeline gain over that control. Support/reuse did not consistently beat lean. DOT browser artifacts are Three.js replays; static packaging checks passed, but rendered QA was blocked by a socket restriction. They provide no browser force-compute throughput evidence.

## Comparison with the supplied E/L proposal

The design in `/tmp/m31-zero-screen-design-challenge.md` is unselected. E keeps current Z’s classifier, actual receiver rotor radius, axis/operator norms, guard ordering and exact retained terms, while removing positive-envelope/capacity calculations and shadow selection/reporting. **That broad zero-only approach has already been tested by DOT support; removing all pair screening was already tested by DOT lean.** It should be described as a controlled reimplementation/simplification of the current M31 path, not a newly discovered algorithm.

L changes only scheduling: it computes the same downstream lo/hi first and exits for `hi<=0 || lo>=cutoff` before forming center radial residuals, `Math.hypot` and rlo. The inspected DOT `zeroSupport` computes its center radial norm eagerly, so that exact center-level intervention is absent there. Downstream-before-radial evaluation already exists in the retained rotor kernel in DOT and current M31 `exactTerm`; the general idea is established. L keeps projection eager and retains near-domain fallback before radial/projection skips. Its saved norm count would be an operation count, not measured CPU saving.

DOT support cannot simply replace E: envelope formulas/margins, accepted coordinate domain, guard and first-error order, arithmetic grouping, array ownership, nominal load inputs and instrumentation differ. Keeping the current Z contract isolates fewer changes. Prior mixed/negative results motivate an explicit comparator choice but predict neither new N=5,000 performance nor f32 validity, and confer no execution permission.

## Audit C1/R8 and the precision boundary

`research/campaign-audit-overhead/implementation/src/branch-audit-c1.cjs` optimizes diagnostic branch auditing, not the wake field: one ordered-pair center distance replaces four repeated distances, and margin/extremum records are allocated only when winning. At N=16, center hypot calls fall from 960 to 240; 960 rotor radial calls, 960 pair objects and 7,680 margins remain. A 75% reduction of one call category is not a 75% runtime or force-query speedup. Its contract includes signed zero, property order/descriptors, alias/nonmutation/error behavior and serialized binary64 bytes.

The original AUDIT-C1 failed admission before its 82 children. Later [R8 postrun status](https://github.com/denghanjie/drone-swarm-aerodynamics-public/blob/1336f5c416875a9651f92b58b2ed06649f25b04e/research/campaign-audit-c1-r8/postrun/MILESTONE.md) supersedes stale “unrun” overview text: 32 controls passed; 218/229 cases completed, one partial and ten unstarted; seven of 18 jobs completed. Terminal EVIDENCE fields are `status:"resource_limited"`, `attempts:1`, `retryAllowed:false`, `fullCorrectnessQualified:false`, **`benchmarkPermission:false`**, `gateExecuted:false`, `benchmarksExecuted:0`. Two complete preflight reproductions, their six original artifact comparisons and four workload contracts remain unrun. The supported stop cause is the child CPU reserve, not per-row fsync; category timers do not identify a bottleneck. R8 remains closed with no retry or resume.

Current M31’s completed static force reference at `3b8273f` covers 12 snapshots, 112,000 rotors and 28,000 vehicles in binary64, using production Newton (max 12 iterations), independent bisection (max 96) and ordinary/Neumaier sum comparison. Its gates are: geometry 1e-12 plus exact domain/tilt classification; inflow 1e-11 +1e-12 relative; rotor thrust 1e-12 N; body thrust 5e-12 N; body moment 2e-13 Nm; world force 1e-11 N; world moment 1e-12 Nm; cubic residual 1e-12; bracket width ≤2e-15; ideal-power identity 1e-14 W +1e-12 relative. It does not qualify f32. Input quantization, geometry predicates, reduction order and receiver-root accuracy would each need explicit treatment in any separately authorized browser port; these gates cannot silently be weakened to M8’s mechanics tolerances.

No inspected evidence establishes an f32 wake-field or receiver-root port, GPU-resident Boids/control/grid, deterministic parallel force reductions, cross-adapter agreement, 5,000 interacting force-query timing, or integrated real-time flight. Temporal-reference failures and the incomplete joint-stage reference also remain distinct from static arithmetic qualification. This audit used only file/JSON/text/hash inspection and bounded remote reads: no checkout, fetch, scientific module import, benchmark, browser launch or hardware experiment.
