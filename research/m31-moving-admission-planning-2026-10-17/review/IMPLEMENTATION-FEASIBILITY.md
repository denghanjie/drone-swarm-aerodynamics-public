## Browser boundary and rounding/transport

The candidate modules use CommonJS require/module.exports and JSON-spec loading. The adapter additionally depends on Node Buffer. These are concrete browser packaging blockers, while the inspected filter primitives already use ordinary Number, DataView and ArrayBuffer (`binary64-interval.cjs:6-32`) and reduced rationals use JavaScript BigInt (`rational.cjs:3-10`). A browser worker could host an explicitly frozen ES-module packaging of this arithmetic with a reviewed DataView replacement for Buffer. That is a feasible architecture proposal, not a tested compatibility result. BigInt, worker loading and chosen-browser behavior would need later capability and conformance gates.

Preserve original words across boundaries. A suitable future wire form is the existing sixteen-hex-digit words, or two explicitly ordered Uint32 words per binary64 value with explicit endianness. Worker structured clone/ArrayBuffer transport can preserve those bytes; the precise schema still needs validation. Do not reconstruct scientific input from Three.js transforms, Float32BufferAttribute, rounded display JSON, decimal formatting or interpolated frames. The current display uses Float32 geometry for wake/cue drawing (`app.js:22,46`); that is acceptable for display only. Keep original full state words and stable IDs distinct from view coordinates and arrival order. Native decimal ingestion, if used at all, needs one stated conversion boundary; already captured words should not round-trip through a textual decimal approximation.

The fixed rotation/constant expression graph matters. `adapter.cjs:6,9-11` uses native multiply/add and sqrt before converting results to exact dyadic inputs. A port that changes expression association, normalizes attitude opportunistically, substitutes another rotation library, or uses f32 values defines different prepared words. Identical raw inputs alone therefore do not prove cross-runtime prepared-state identity. A later browser conformance protocol must compare constants and every prepared word, followed by complete scientific results or an explicitly justified weaker invariant. The current filter's own stated assumptions include binary64 arithmetic, gradual underflow and no reassociation/fusion (`binary64-interval.cjs:3-4`). No new cross-engine rounding guarantee is inferred here.

The historical GPU receiver wrapper is useful lifecycle precedent, not a compatible whole-kernel implementation. `research/m31-browser-receiver-2026-10-16/source/browser.js:5-22` checks adapter/device limits, fallback status, shader compilation and validation; lines24-40 marshal groups of four Uint32 words, allocate input/output/readback buffers, dispatch, await mapping, and destroy resources; lines44-46 expose health/validation completion. That interface is not the seventeen-binary64-word drone input plus complete coefficient/load/certificate schema. Its shader was not read under this cap, so this review makes no claim about shader arithmetic. Translating the current BigInt/Number/interval graph to GPU code would require its own numerical design and proof; word packing alone would not transfer correctness.

Putting work in a worker can keep the UI responsive and isolate message ownership. It does not reduce total exact arithmetic by itself. Queue delay, copying, preparation, kernel computation, certificate construction, return serialization and UI rendering would need separate boundaries in a future end-to-end study. Dropping queued frames is a product policy that must not silently remove failed or slow states from a research denominator.

## Avoidable repeated work: source hypotheses, not timings

Several concrete repetitions deserve consideration before a platform race. None has a measured speed contribution in this review.

1. **Self-state preparation is duplicated internally.** `methods.cjs:8` calls `A.prepare({receiver:d.state,source:d.state})` and keeps only the receiver. `adapter.cjs:14` decodes, prepares and validates receiver and source independently, even when they are the same array. One preparationCalls increment does not mean one internal prep/validation. A dedicated single-state path could avoid that duplicate while preserving the raw validation and rejection semantics. Its equivalence must be checked prospectively, not assumed from the counter.
2. **Force-only factors repeat across active pairs.** `pair-prepared.cjs:25` recomputes nominal source force/beta for each active source interaction and nu for each receiver rotor/source interaction. The source factor is constant for that source within a snapshot, and the receiver normalization is constant for that receiver rotor. Frame-local lazy memoization could retain the identical arithmetic result. Eager precomputation is unsafe as a semantic shortcut if an operation would throw/unresolve before an original earlier zero/rejection branch: preserve original first-use/exception priority and charge cache creation/storage.
3. **Some geometry repeats across rotors.** `pair-prepared.cjs:14` calculates the same center squared norm for its guard and neighbor test, and repeats center-only work across all four rotor queries of a directed drone pair. Projection in line18 also does not depend on rotor. The filter has a similar center stage (`zero-filter.cjs:11-17`). Exact directed-pair sharing or a batch-of-four query could reduce repeated work, while rotor-specific down/radial tests still differ. Do not introduce a full N-squared retained cache by default; a bounded local cache or batched residual worklist needs its own memory/coverage argument.
4. **Repeated native proposal conversion is visible.** `loads.cjs:28-35` revisits each positive coefficient on every candidate iteration and converts the same fixed96 midpoint through Number each time. Precomputing that identical native midpoint per positive term would target repetition without changing the exact certificate arithmetic. It remains a candidate-only calculation; changing operation order or convergence policy is a different intervention.
5. **Prepared values are decoded again downstream.** `methods.cjs:14`, `loads.cjs:22,25,61` reconstruct forces/axes or native force words at separate stages. A per-snapshot immutable internal prepared object can hold exact/native views and still produce the same saved word record. Any ownership change must prevent stale reuse or mutation across methods/snapshots.
6. **Exact rational normalization and hierarchy work remain.** Every add/subtract/multiply/divide calls reduced-rational construction with gcd (`rational.cjs:3-5`), and tree construction repeatedly computes exact bounds and sorts (`tree.cjs:13-19`). This is a plausible CPU/allocation cost, not evidence that gcd or tree building dominates. A dyadic-specialized representation, node refit, or changed traversal is a deeper numerical/structural change and should not be bundled into a first browser port.

The unchanged call currently starts from fresh state and reconstructs everything. For moving states, centers, points, axes, tree bounds and membership generally change, as can rotor forces, positive edges, rank order and certificate boxes. Cached prior-frame proof/zero claims cannot simply survive motion. A future reuse design should first reuse within the same immutable snapshot. Across frames, constants are simplest; unchanged force or attitude word groups can be keyed exactly, while positional/global/tree effects still need recomputation or a separately proved update rule. Small numeric displacement is not proof that a branch, bound or certificate is reusable.

A tilt can widen global or node axis bounds, increasing residual queries, even if total drone count is unchanged. A source/receiver approaching a cutoff can cause fast-filter uncertainty and exact fallback. Actual controller/integration state can also produce force/preparation/order refusal. Those are new admission and workload questions, not costs that the six upright cases have already answered.

The closed filter-cost audit in the previous work is inherited evidence, not rerun here: dense median paired filtered/hierarchy ratios were approximately0.6830,0.6211,0.6513, and all24 measured pairs favored filtered. The180-drone dense filtered median was about3.891 seconds. Across one representative call per scene, the exact hierarchy left72,271 scalar pairs; the filter proved47,891 of those zero and left24,380 exact calls. These figures support a useful finite static filter benefit while also showing substantial remaining work. They do not identify its cost breakdown, predict moving-state hit rates or scale to5,000 drones.

The prior audit also reported only5,880 positive entries across those representative scenes. That observation does not justify omitting any logical pair or retaining the old storage/support assumptions for moving states. Full proof construction, geometry, traversal and zero discovery remain part of the evaluated service. Source-only repetitions above motivate a future comparison; they are not new measurements or established priority among phases.

## Remaining uncertainty and decision

The leaf-box helper, fixed96 interval helper, underlying flight controller/integrator, old aerodynamic integrator, grid/geometry/course modules, GPU shader and saved full trajectory data were not read in this desk stage. The cap is reached. The caller shows useful integration seams but does not prove the internals' semantics, attitude normalization, reproducibility, locality, complete dependencies or the exact future runtime's browser behavior. Those require a fresh bounded review allocation before a successor is frozen; no missing detail is filled with a claim of compatibility.

The main transfer risk is currently that actual changing flight states fail the exact domain/order/certificate contract or yield an uninformative all-zero subset. The main implementation risk is spending effort porting repeated exact work whose cost is not intrinsically tied to Node. A brief, precommitted full-state admission diagnostic resolves the first risk; carefully isolated within-snapshot reuse targets the second. A new browser speed result on another small upright group resolves neither strongly enough to be the next priority.
