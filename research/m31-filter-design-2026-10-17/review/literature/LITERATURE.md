# Verified literature for a prospective scalar-zero filter

Status: design evidence only, 17 October 2026. The recommendation is a **branch-preserving zero-only interval filter, followed by the unchanged exact scalar query whenever uncertain**. This is a known numerical-filter pattern applied prospectively to the declared scalar graph. No algorithm novelty, performance gain, physical validation, new admitted domain, or implementation correctness is established here.

## Primary sources and versions

**[SHEWCHUK1997]** Jonathan Richard Shewchuk, *Adaptive Precision Floating-Point Arithmetic and Fast Robust Geometric Predicates*, Discrete & Computational Geometry 18(3), 305–363 (1997), [DOI](https://doi.org/10.1007/PL00009321). Reviewed the [author-hosted full report](https://people.eecs.berkeley.edu/~jrs/papers/robustr.pdf), CMU-CS-96-140R, cover dated 1 October 1997, 59 PDF pages; it explicitly identifies the journal article. This is the revised long report, not the 1996 short conference paper. Its About-this-report page carries a 1998 copyright. The [author page](https://www.cs.cmu.edu/~quake/robust.html) and Crossref independently corroborate title and journal details; the file pin identifies the precise reviewed bytes.

The complete §3 (printed pp.27–30; PDF pp.31–34) explains approximate evaluation, error-bound tests and successively more accurate computation with exact fallback. Its value for this design is the acceptance discipline and the recognition that additional filter stages impose overhead when exact computation is still required. The determinant-specific error constants and performance measurements are not transferable to this scalar model. §2.1 (printed p.3/PDF p.7) explicitly states that the article “does not address issues of overflow and underflow.” §5 and the conclusion (printed pp.47–49/PDF pp.51–53) warn about compiler transformations, excess precision and finite exponent-range limitations. The [author PC caveat](https://www.cs.cmu.edu/~quake/robust.pc.html) reinforces that implementation assumptions matter.

**[BBP2001]** Hervé Brönnimann, Christoph Burnikel and Sylvain Pion, *Interval arithmetic yields efficient dynamic filters for computational geometry*, Discrete Applied Mathematics 109(1–2), 25–47 (2001), [DOI](https://doi.org/10.1016/S0166-218X(00)00231-6). Reviewed the complete relevant sections of the [author-linked HAL manuscript v1](https://inria.hal.science/inria-00344281v1/document), deposited 4 December 2008. The 22-page PDF includes a HAL cover and manuscript pages 1–21, so these locators are not journal page numbers. The [author publication list](https://www-sop.inria.fr/members/Sylvain.Pion/publications/) and Crossref distinguish this journal version from the 1998 conference paper, DOI 10.1145/276884.276903.

§2 (manuscript pp.3–5/PDF pp.4–6) defines the essential contract: “A filter never returns a wrong answer” but can return “NO IDEA.” More accurate filters or exact computation handle that outcome. §§3.1–3.2 (manuscript pp.5–6/PDF pp.6–7) give interval inclusion operations and outward-rounded endpoints; an interval containing zero generally cannot decide a sign. Division by a zero-containing interval is uninformative; square-root domain changes need separate mathematical justification. The introduction (manuscript p.3/PDF p.4) identifies two limitations: exact-zero recognition often fails, and repeated/dependent operations can make intervals very wide. Locally tight operations do not imply a globally tight expression enclosure. We use these principles, not the paper's determinant algorithms or its old hardware timing factors.

**[MP2007]** Guillaume Melquiond and Sylvain Pion, *Formally certified floating-point filters for homogeneous geometric predicates*, RAIRO - Theoretical Informatics and Applications 41(1), 57–69 (2007), [DOI](https://doi.org/10.1051/ita:2007005). The author's HAL link `inria-00344376` serves the [inria-00071232v2 manuscript](https://inria.hal.science/inria-00071232v2/document), deposited 4 December 2008. The cover, landing metadata and Crossref agree on the journal identity. Publisher-layout placeholders remain in the manuscript; the publisher PDF returned HTTP 403, so this review does not claim version-of-record byte verification.

The full substantive manuscript was reviewed. §§2.2–2.3 (manuscript pp.3–5/PDF pp.4–6) explain overflow, gradual-underflow error, double rounding and explicit uncertain fallback. §§3.2–3.4 (manuscript pp.6–9/PDF pp.7–10) show expression-level induction and emphasize that computing the error bound can itself round downward and invalidate a test. §4 limits the demonstrated generalization to homogeneous predicates. This is strong support for proving the whole executed expression and its exceptional cases, but not permission to transplant its orientation error constant or claim our branch-heavy rational expression has already been formally verified.

## Proposed use in this model

The current design draft and inherited `pair-prepared.cjs` were read as text only. The candidate applies after unchanged admitted preparation. It returns either a certified existing **zero branch** or **unknown**. Unknown invokes the unchanged exact query and returns that query's full result, including rejected/unresolved/positive outcomes. No approximate positive coefficient is returned. The unchanged positive profile, square roots, certificate, loads and acceptance tolerances therefore remain outside the filter.

The soundness obligation is: for every admitted prepared input, if the filter returns zero with branch B, the unchanged exact query returns the same zero branch B and its canonical zero payload. Otherwise the wrapper returns the unchanged query result. It is insufficient to prove only that a later expression is nonpositive: earlier guards, rejection branches and earlier zero branches have priority.

| Ordered candidate | Necessary prefix and zero proof |
|---|---|
| Neighbor | Prove the center guards do not reject, then prove center-distance squared is at least the exact neighbor threshold squared. |
| Upstream | Prove neighbor is not selected; rotor and down guards pass; prove down is at most zero. |
| Down-cut | Prove earlier guards/branches are excluded and down is at least the exact cut. |
| Near-outside | Prove earlier exclusions and radial guard; prove down is strictly below minDown × D and radial squared is at least nearRad squared. Never turn the near-invalid case into zero. |
| Radial | Prove the near branch is not selected, width is strictly positive, then radial squared is at least (radCut × width) squared. |
| Projection | Prove all earlier guards and zero/rejection branches excluded, then raw axis projection is at most zero. |

These are design obligations inferred from the inspected scalar source, not published results about this model. Use the actual residual `d - (d dot axis) * axis`; a near-unit axis must not be silently replaced by an exactly unit vector identity. No square root is required for these zero decisions.

## Required enclosure and implementation proof

1. **Input identity.** Decode each finite prepared binary64 word as its exact dyadic value and initialize a singleton. For any derived threshold, enclose the exact expression over the same constant words. A rounded evaluation of an exact rational expression is not an exact singleton. Keep admission and constant provenance unchanged.
2. **Every operation encloses.** Prove add/subtract/multiply/divide enclosure from operand enclosures. Use all required endpoint products/quotients and a justified square operator if added. Reject malformed, NaN or infinite intermediates/endpoints; a denominator enclosing zero is unknown. Sound loss of precision must produce unknown, never a guessed sign.
3. **Runtime semantics.** The retrieved [ECMAScript specification](https://tc39.es/ecma262/multipage/ecmascript-data-types-and-values.html), §6.1.6.1 and its multiply/divide/add/subtract clauses, specifies binary64 roundTiesToEven results and subnormal Numbers. This is a normative premise, not evidence that a finite platform test proves conformance. Freeze the runtime identity and the executed operation order; no unproved fused, reassociated or fast-math substitution.
4. **Adjacent-value widening.** Conditional on a correctly rounded finite primitive result `r`, enclosing the exact primitive result between the predecessor and successor of `r` is conservative. It is generally wider than the tight directed-rounding interval described in BBP2001. Widen every primitive endpoint result, not merely the final expression. The exact ordering argument extends to gradual underflow; it does not depend on a relative-error bound near zero. A correct adjacent-value implementation must handle both signed zeros and the minimum subnormal, powers of two, negative values, maximum finite values and infinite neighbors. Refuse the fast path at any unsupported range boundary. No runtime rounding-mode change is assumed.
5. **Comparison semantics.** For independent enclosures X=[Lx,Ux], Y=[Ly,Uy], `X >= Y` is proved by Lx >= Uy and its strict negation by Ux < Ly; `X < Y` is proved by Ux < Ly and its negation by Lx >= Uy. Analogous reversed tests handle the other comparisons. Overlap means unknown. Closed versus open thresholds must match each original branch exactly, including equality and signed zero. If prior branch exclusion is unknown, fall back immediately.
6. **Complete branch preservation.** Carry the prefix proof through the original guard/branch order. Do not skip an earlier center, rotor, down, radial, near or width rejection merely because projection or a later exclusion looks decisive. A proven earlier rejection may simply return unknown so the original query emits the canonical rejection.
7. **Unchanged scientific evidence.** Independent checking must compare exact branch/status and canonical zero outputs, exercise uncertain fallback, and preserve complete positive/reference validation and all declared load tolerances downstream. A high filter-hit rate, matching rounded values or a few random cases do not establish soundness.

## Binary64 intervals are not arbitrary precision

Outward rounding gives containment under its premises; it does not increase binary64's 53-bit significand or exponent range. Cancellation, dependency, nearly equal thresholds and exact equalities can keep a result undecidable. Repeating the same fixed-precision interval calculation does not refine it. True input uncertainty also cannot be removed by exact arithmetic; this design instead treats frozen input words as exact data, as BBP2001's predicate setting does.

Expansion arithmetic (Shewchuk) can add precision for suitable arithmetic while retaining hardware exponents and strict rounding assumptions. Arbitrary-precision floating point is another choice, but is still rounded arithmetic. The retrieved [GNU MPFR 4.2.2 manual](https://www.mpfr.org/mpfr-current/mpfr.html), §§4.2–4.4, documents selectable precision, bounded configurable exponents and explicit RNDD/RNDU rounding. It does not make every rational or algebraic result exact, and MPFR has no native subnormals (IEEE behavior requires deliberate emulation). This manual clarifies the distinction; MPFR is not installed, run or adopted here.

The existing fallback combines exact rational operations with a separately bounded 2^-96 directed interval layer; its explicit range/admission rules remain authoritative. The proposed filter does not expand that admitted domain. An adaptive precision ladder, new algebraic-number backend, positive-coefficient substitution or native transcendental approximation would each require a separate design and proof.

## Prospective validation and decision

No numerical experiment was performed. Before a new bounded allocation, freeze primitive enclosure tests against an independent exact reference; branch-boundary and adversarial cases; mandatory unknown/fallback cases; malformed/range cases; and deliberate faults targeting inward endpoints, wrong equality, skipped guards and unsafe normalization. Count all filter work and fallback work if a later total-cost experiment is authorized. Separate primitive correctness/branch preservation from any later performance experiment. Do not retune using the closed timing suite. Filter overhead and exact fallback may erase gains; exact reuse/caching remains a competing explanation or future alternative, not a result here.
