Static adversarial critique of the possible M31 complete-query feasibility protocol

2026-10-16. This is an analytical design challenge, not an adopted protocol, implementation, freeze, numerical result or launch permission. It follows `../../m31-coordinate-origin-2026-10-16/next-question/WHOLE-OBSERVABLE-BUDGET-AUDIT.md`. Only existing source/protocol/report text was read. No scientific module was imported; no generator, numerical script, geometry, wake, reference/root solve, checker, browser, GPU operation, benchmark or dynamics was executed. No repository file was changed.

The proposed question is legitimate, still missing and potentially useful: can one fixed complete browser implementation of the assumed static wake/load model deliver the selected observables within independently chosen engineering tolerances? Existing CPU complete-query work and finite GPU component campaigns do not answer it. Retaining primitive A is legitimate if this is explicitly a new complete-output contract with new data and one disclosed, exposed architecture choice. It must not be described as a coordinate-campaign confirmation, an old strict-component pass, physical validation or algorithmic novelty. A new receiver implementation also cannot inherit the fixed-hover receiver's qualification.

The coordinator subsequently narrowed the prospective scope to a **complete field-to-body-load static query**: every receiver's wake sums, effective rotor forces using the prescribed nominal motor states, body thrust and all three body moments with nominal yaw. World rotation, control, RK4 and held-flow dynamics are explicitly excluded; no benchmark is proposed. That scope is coherent and avoids a world-output gate. This memo assesses that narrowed proposal below; it does not adopt it.

The proposal is **not ready to freeze**. Its most consequential unresolved choices are the new yaw target; exact input/preprocessing ownership; the motor/underflow/receiver domain; concrete work and byte caps; and reference/convergence gates. The narrowed claim resolves the earlier world-output ambiguity, and a direct-body-gate/combined-field-diagnostic design resolves the earlier isolated-term-reserve conflict. Remaining choices can be resolved statically. They are not reasons to start generating scenes or probing the GPU.

**1. Fix what “complete” includes and what stays unchanged**

Primitive A identifies world-point subtraction in the wake term. It does not specify the complete architecture. Freeze whether host JS derives axes and rotor offsets from original binary64 quaternions and uploads their f32 representations, or whether the GPU derives them from packed quaternions. These differ numerically and operationally. A coordinate experiment that supplied host-prepared axes/offsets does not qualify GPU quaternion preparation. Likewise fix the grid/neighbor or direct-all-pairs traversal, deterministic source order, reduction graph, receiver parameter construction, body assembly, output ownership, and upload/readback boundaries. “Ordinary f32” alone leaves all of these open. World output rotation is excluded under the narrowed decision, while orientation preparation for the wake remains in scope.

An original-state reference R must use original positions, orientations and lagged motor values. The represented-input path Q must evaluate the **actual decoded interface**. Rounding a 17-state vector and calling I is not the same Q as rounding already prepared axes/offsets and calling a prepared-input evaluator. Independently rounded nominal force and vi also define a different represented receiver from computing vi from rounded nominal/rho/area. Pin exactly which one is intended. Q is an attribution path; agreement with Q never replaces original-input agreement.

Retain the assumed source wake strength at isolated hover even when source motor inputs are zero or unequal. This is a known model assumption, not a coherent source-thrust-feedback model. Preserve the strict center cutoff, tilt gate, near-domain rejection, radial/downstream branches and original nominal-yaw policy. A zero nominal receiving rotor may return zero force but must not silently bypass the field's required domain/policy checks. A zero-motor source still emits the prescribed source wake in this model.

The existing M28 source uses host states and varying lagged motors, with held winds and host RK4; M31's inspected simulator has airflow off. A complete static browser body-load query is useful but still is not an integrated aerodynamic simulator. In particular, a once-per-query body load does not replace the application's held-wind interface: the application reevaluates receiver forces from changing motor states during RK stages. Arbitrarily generated values in motor-state slots should be called **prescribed lagged-motor-state inputs**, not observed or dynamically reachable flight states unless that additional provenance exists.

**2. Output budgets: plausible historical anchors, incomplete specification**

The historical `0.005mg` thrust and `0.0005mgD` roll/pitch targets predate the GPU failures, which makes them defensible candidates for an independently motivated model-fidelity question. Their original meaning was an analyst-selected positive-omission allowance, not a measured application tolerance. The new protocol must explicitly adopt or reject them for this different generic two-sided complete-pipeline purpose before outcomes. The old `2a` one-sided moment advantage cannot be reused.

For arbitrary per-rotor errors `e_k`, exact assembly gives `abs(deltaT)<=sum(e_k)` and each roll/pitch error at most `a*sum(e_k)`. Add actual assembly arithmetic separately. A uniform per-rotor planning allocation must satisfy both `4e <= epsilonT` and `4ae <= epsilonMoment`, after other reserves. No positive omission means there is no omission error to spend, but it does not make every other reserve free. Do not add a new budget to a historical budget while claiming the same total target.

Yaw is now nonzero in general and needs its own explicit tolerance. With `k=km/kf`, the intended yaw is `k*(n0-n1+n2-n3)` using **nominal** lagged motors, not wake-reduced forces. Motor representation, the representation of k and assembly all contribute; generic motor errors `d_k` contribute at most `abs(k)*sum(d_k)` before those other terms. Comparing against zero yaw would be wrong for unequal motors.

Using `epsilonYaw=.0005mgD` is defensible as a **new** common engineering moment scale selected before outcomes, if that rationale and its limited model-fidelity meaning are stated explicitly. It is not a historical yaw target or evidence that yaw-control sensitivity is comparable to roll/pitch. No saved failure should be used to select it. “Metadata/reference check only” is not an alternative way to qualify yaw accuracy without a target: a numerical reference comparison still needs an acceptance rule. If yaw is excluded from primary numerical acceptance, the claim must exclude yaw accuracy rather than say all three body moments were qualified. For the proposed all-three-moment scope, my recommendation is an explicit prospectively chosen yaw target, with the same scale an admissible engineering proposal rather than an inherited fact.

Under the narrowed **body-load query** decision, world force and world moment are excluded and should not be computed merely to make an unused output table look complete. No world-rotation or complete `I.loads` equivalence claim follows. A future extension that delivers world vectors would need prospective vector norms/tolerances, orientation/rotation error and actual numerical map-norm allowances. The present body contract deliberately stops before that computation.

Reference error and model discrepancy must remain distinct. A small numerical reserve for the independent solver is meaningful if checked. A supposed reserve for the physical model is not established merely by naming it: this model's receiver closure, source amplitude, finite support, aggregation and missing wall/ground/history effects remain unvalidated. Engineering targets against the assumed equations support numerical feasibility only.

**3. Variable nominal force is a new receiver domain**

The qualified receiver shader admitted fixed uploaded nominal/vi constants, with guard ranges `f0 in [.01,.1]`, `vi in [1,10]`, and `U in [0,128]`; it has no nominal-zero branch. The current controller's command maximum is `2.25*mg/4`, which exceeds `.1 N`. Zero and arbitrarily small positive motor inputs also fall outside that qualified component. The old pass cannot be cited as verification of this new domain. A controller command clip is not by itself a proof of all lagged-state/integrator-stage bounds; define the proposed static state admission explicitly.

For positive nominal n and coherent ideal `vi=sqrt(n/(2*rho*A))`, inflow sensitivity is `L(n)=sqrt(2*rho*A*n)/3`; use each rotor's value or an explicit bound at the admitted maximum. At `n=0`, force is identically zero and the displayed n/vi formula must be replaced by the zero branch. The fixed-hover sensitivity cannot be silently reused at larger motors; at `nmax=2.25*fhover`, the ideal sensitivity bound is `1.5*L(fhover)`.

There is also a useful analytical bound for coherent nominal representation. For fixed U, differentiating `F(n,U)=n*x(U/vi(n))` gives

`dF/dn = 3*x*(1+x^3)/(2*(1+2*x^3))`, for `0<x<=1`.

This expression increases to 1, so the ideal force is 1-Lipschitz in n, continuously including n=0. This can motivate a nominal-input reserve. It does not bound separately rounded rho/area/vi construction, f32 arithmetic or final multiplication; those remain separate. It is a desk derivation, not an empirical certificate.

Do not confuse the coordinate admission `abs(position)<=128 m` with an inflow admission `U<=128 m/s`. They are unrelated. The old all-receiver field has not established the latter for arbitrary new dense scenes. Either freeze a justified finite inflow domain with terminal rejection, or derive a conservative bound from N, support/decay and admitted axis norms. For example, a real-arithmetic coarse bound can use `(N-1)*sourceInduced*decay/(minDownstream-origin)` times a projection-norm bound, because fades/radial attenuation are at most one. Such an argument still needs the actual numerical assumptions and guards; its value must not be selected by observing the fresh field.

**4. Static assessment of the proposed scaled Newton receiver**

The coordinator's proposed new method is analytically reasonable, conditional on positive finite n and vi and nonnegative finite U:

- If `U<=vi`, set `alpha=U/vi`, solve `x^3+alpha*x-1=0`, start at x=1.
- If `U>vi`, set `r=vi/U`, solve `r*x^3+x-r=0`, start at x=r.
- Run exactly twelve Newton updates and return `n*x`, with separately specified n=0 and U=0 identities.

For the first branch, `alpha in [0,1]`; the root exceeds 2/3 because `(2/3)^3+2/3-1<0`. The increasing convex polynomial is nonnegative at x=1, so exact Newton iterates decrease from above toward the root and retain a positive derivative. For the second branch, `r in (0,1)`, `g(r)=r^4>=0`, `g'=1+3*r*x^2>=1` and `g''=6*r*x>=0`; exact Newton from r likewise decreases from above. Both equations have the same positive root as the original law. The scaling avoids constructing a potentially enormous positive alpha in the U>vi branch.

These facts do **not** prove twelve f32 updates attain any specified force error. The previous shader starts differently and uses a different expression; its empirical result is not inherited. The new source must freeze operation grouping, coefficient construction, branch comparison and update count. Do not call the fixed twelve-update status “converged” by definition. A residual and finite/range checks plus independent force/root comparisons are necessary finite evidence. No clamp or alternate fallback should silently repair an invalid iterate.

The underflow contract is a blocker unless made explicit. Distinguish at least:

| Situation | Required semantic/evidence distinction |
|---|---|
| Original n is exactly zero | Explicit identity, effective force zero; define root/alpha diagnostic conventions without dividing by zero. |
| Original n is positive but packs to zero | Record original and packed bits and count representation loss; it is not an original physical zero. Decide prospectively whether permitted as approximation under final gates. |
| Packed n is a positive subnormal | Record raw words; arithmetic may treat it differently under allowed backend behavior. Passing finite controls is backend evidence, not a portability proof. |
| n>0 by raw bits but computed vi is zero | Record coefficient underflow/arithmetic-zero status. It cannot be mislabeled a valid positive-vi root solve. If the protocol permits a resulting force approximation, that must be explicit before data and still pass delivered-output gates. |
| Computed r or final n*x becomes zero | Record ratio/product underflow separately from exact identities; a finite zero is not evidence that the original force was exactly zero. |
| U is zero, both inputs are zero, or signed zero appears | Freeze priority and canonical output/metadata conventions. Do not divide first. The old force comparison does not automatically prescribe signed-zero equivalence. |
| Negative, NaN, infinity or out-of-domain words | Inspect raw representation as needed, reject with an explicit complete invalid record and no valid-looking default output. |

The coefficient path also matters. Computing `n/(2*rho*area)` with packed constants differs from an uploaded precomputed vi, and factoring/inverting the denominator changes floating behavior. Normal inputs, subnormal inputs and operation results need separate treatment. A finite packet of controls should cover exact/adjacent branch cases at U=vi, zero identities, small and maximum n, tiny positive U, ratio/product underflow, unequal motors and invalid values. The scalar list and expected semantics must be finite and frozen, not an open-ended search for a passing range.

Keep the unscaled original independent bisection as the original-model force reference where its admitted finite range is valid. The fact that the candidate uses a scaled equation is not a reason to replace the reference with the same algorithm. If the new declared range exceeds the existing oracle's finite-alpha capability, resolve that reference range or independent extension statically before launch. Retain alpha or r with a branch tag; do not record r under a field called alpha. Recompute dimensionless residuals in binary64 from saved operands for each declared equation; the shader's residual alone is not an independent check.

**5. Totals-only evidence is valid for a narrower claim; reserves are not proofs**

Direct final-body-output gates against original I, combined with complete policy/validity checks, can establish finite observable-level agreement without retaining full term matrices. In the coordinator's narrowed design, R/Q/GPU inflow totals are **combined field discrepancy diagnostics**, not an independently qualified field-error bound. They support original-to-represented and represented-to-GPU attribution but do not isolate term-generation error from summation error, prove an L1 term bound, or independently reconstruct the sum of actual GPU terms. Old strict L1 results stay separately failed; the future experiment must not state that it met them.

Body thrust/roll/pitch can be accurate while individual rotor forces are inaccurate. Errors proportional to `[d,-d,d,-d]` vanish in all three of those observables; nominal yaw is independently assembled from nominal motors and therefore does not remove that nullspace. Retained per-rotor outputs should expose this possibility, with finite/range/status requirements, but diagnostic rotor comparisons are not separate rotor-accuracy qualification. This is an acceptable limit for the explicitly body-observable question, not evidence that the receiver component as a whole passed a force tolerance. Avoid describing a final body pass as a new receiver-only pass.

Separately named term and sum “reserves” can be planning allocations only until backed by appropriate evidence. With no retained terms, choose one honest combined field allowance for acceptance/attribution or supply a separate valid analytical certificate. Do not present a spreadsheet of reserves as a verified end-to-end bound. An aggregate direct comparison is still useful; its limitation is specific rather than fatal.

Original ordinary and Neumaier totals from the same pass give a numerical consistency check, not independent physical or exact-real reference truth. Exact dyadic accumulation performed online over ephemeral terms could strengthen runtime numerical evidence, but without those terms a saved-only reviewer cannot reconstruct that exact sum. A checksum of discarded terms detects some provenance changes; it does not replace their numerical evidence. State clearly which checks are independently reproducible from saved operands and which are supported only by frozen source plus recorded runtime assertions.

Retain original states, exact uploaded words, source/config/runtime hashes, all declared R/Q/GPU sums, per-rotor nominal/vi or ratio inputs, delivered rotor forces, solver branch/count/status/root/residual records, body outputs, complete policy and write-validity records, and failure prefixes. Saving each delivered rotor force permits saved-only independent wrench recomposition under an explicitly authorized verifier; that is additional bounded arithmetic, not a free scientific rerun. World-output records are unnecessary under the narrowed scope. The present audit performs none of this verification arithmetic.

**6. The reference plan needs more precision than “I plus an existing CPU path”**

Original I already supports varying nominal motors and independent bisection via `receiverSolution`/`receiverWrench`. The current source-omission `loadRows` adapter instead hardcodes f0 and zero nominal yaw; it is not a valid unchanged comparator for the proposed motor sweep. Use the existing underlying M28 `effectiveThrust` and wrench semantics in a separately frozen pure-body-load adapter if that is the selected second path; do not integrate trajectories to obtain a static reference. A new adapter itself needs static review and current-domain checks. DOT alternatives have different ownership/domain contracts and cannot be called interchangeable without pinning them.

For original I, avoid an accidental duplicate solve: calling `receiverWrench` or `loads` computes roots internally, so separately calling `receiverSolution` again merely to save diagnostics would repeat them. Freeze an adapter that reuses each planned returned root/force record for body assembly, or explicitly charge any genuinely intended second solve. `loads` also performs world rotations outside the narrowed scope. These source-call consequences should be resolved before the work ledger is frozen.

For every original or represented root reference actually used, predeclare finite admission, root bracket/width and residual checks, maximum iterations and zero conventions. Existing I uses at most 96 bisections, can stop on floating equality or midpoint stagnation, and supplies numerical brackets; it is not an outward-rounded interval solver. A numeric bracket is useful finite evidence but not a universal rigorous error enclosure. Retain force-scaled width, since nominal force varies, and compare the production CPU Newton path with I on the new domain rather than assuming historical fixed-hover qualification transfers.

Original R roots at U_R alone cannot isolate the candidate receiver error at U_GPU. If the protocol wants that decomposition, reserve independent roots at the actual GPU inflows/nominal parameters during the sole charged attempt, after raw GPU results have been persisted. If it only wants direct delivered-force agreement with the original complete query, those extra roots are optional and the root attribution claim must be narrower. Similarly, a returned-ratio reference addresses solver arithmetic at that ratio; it does not remove coefficient or division error from the delivered-force comparison. Count every such root path and maximum iteration explicitly. A saved-only review must not silently solve them later.

For static query feasibility, numerical convergence means the reference/root/sum checks just described. Timestep refinement is not required for a claim that expressly excludes dynamics. If the project later claims trajectory/application accuracy, stale-flow cadence, integrator stage coupling, timestep refinement and model validation are separate unresolved work; a static force pass cannot substitute for them.

**7. Fresh geometry and motor coverage must avoid both triviality and uncontrolled domain failure**

The previous ±128 m position admission is an implementation range, not validated accuracy throughout that cube. Explain why that finite domain is relevant to the source/frame contract and choose representative translations/near-range cases prospectively. Do not use intentionally f32-exact canonical geometry as main acceptance evidence. Record nonzero packing losses without tailoring the generator to observed error. Sizes including 5,000 establish finite shape coverage, not independent evidence for every density or coordinate range.

“Minimum lattice spacing admits near-domain” is ambiguous and must be resolved. A valid main scene needs a predeclared construction whose bounded jitter, rotor offsets, tilts and norm errors respect the near-domain policy, or it risks a terminal rejection before the complete query is available. Center spacing alone is not rotor-to-source clearance. In ideal unit-axis geometry a sufficient separation bound can be derived from maximum rotated arm radius plus `sqrt((minDownstream*D)^2+nearFieldRadius^2)`; actual numerical/nonunit and jitter allowances must also be handled. This is a static sufficiency argument to develop, not permission to test geometry and keep a favorable seed. Keep separate explicitly expected-invalid fixtures for near-domain and tilt rejection. Unexpected main-domain rejection stays terminal with no reseed.

Include unequal motors, zeros, the declared maximum, and small positive values in a deterministic finite assignment that exercises force and moment outputs. Ensure that admitted main cases include a prospectively fixed amount of nonzero wake exposure on positive-motor rotors and nontrivial moment cases. Otherwise a scene dominated by zero motors can pass all delivered-load targets despite poor field calculation. Required policy/field checks remain even for zero motors. Do not choose exposure thresholds from fresh output or from convenient multiples of a failed old epsilon.

The exact-policy requirement is strong: ordinary f32 may change a boundary classification even if force error would be negligible. Keep that rule if chosen. Do not introduce a post-result boundary exception or reinterpret a wrong near-domain decision as acceptable under the force allowance.

**8. Packed policy evidence and bounded execution need concrete accounting**

There are eight policy values (0 through 7), not four. Four rotor codes per source/receiver pair require at least 12 bits before validity/sentinel information. “Packed four codes” must specify a word layout. A u32 with four byte codes costs `4*N*N` bytes per path; a u16 with four nibbles costs `2*N*N` bytes and needs explicitly reserved invalid/unwritten meanings. Code zero is a valid self/outside class and cannot identify an unwritten buffer. If parallel rotor invocations update the same packed word, ordinary read-modify-write creates a race; assign one writer or freeze a correct synchronization/layout scheme.

At N=5,000, there are 25,000,000 ordered pairs and 100,000,000 rotor policy slots. A four-byte pair word is 100,000,000 bytes per path, or 300,000,000 bytes for R/Q/GPU policy payloads alone. Even a two-byte pair layout is 150,000,000 bytes across three paths. These are exact shape counts, not measured memory. Add validity, outputs, roots, source inputs, invalid fixtures, additional sizes/translations, copies, readbacks and failure reserves; do not assume compression saves the cap. The old coordinate resource budget cannot simply be reused.

Complete policy evidence may require all-pair work even if term evaluation uses a local neighborhood. The original I directly checks every ordered pair and only evaluates rotor profiles for eligible neighbors. A 5,000-receiver reference is 1,250 times the previous four-receiver receiver count at the same source count; this is a shape comparison, not a runtime extrapolation. R, Q, the production CPU comparator, additional conditional roots and every translation/size all count. Freeze concrete work ceilings, live/cumulative buffer bytes, submissions, maximum batch work, readbacks, evidence bytes, per-stage deadlines and external process containment before any launch. No analytical count guarantees an adapter will finish under its deadline.

If chunking is necessary, fix it beforehand, including sum order/accumulator lifetime and exact evidence ordinal mapping. Do not change chunk sizes after a timeout. Persist complete raw returned buffers before dependent assessment; reserve failure evidence and retain completed prefixes. Expected-invalid fixtures need explicit partial-record semantics because I throws on near-domain failure before emitting a complete receiver. Missing suffixes cannot be zero-filled into a valid policy matrix. Every required main receiver and declared output must complete for an all-receiver pass.

“No benchmark until correctness” is necessary but insufficient. A correctness pass does not itself authorize a new benchmark. If future timing is planned, separately freeze permission, the complete application boundary, comparator instrumentation and evidence/readback overhead. A direct all-pairs instrumented correctness implementation may be useful feasibility evidence without being the architecture to call fast. Do not optimize away policy evidence, change the traversal, or switch kernels after success and transfer qualification automatically.

**Decision**

Continue static design only. The narrowed field-to-body-load API and combined-field diagnostics are coherent decisions in the proposal. Resolve the remaining contract areas, particularly (a) an explicit new yaw target for the all-three-moment claim, (b) motor/underflow semantics for the new scaled receiver, (c) original/represented reference interfaces and nonduplicated root calls, and (d) realistic shape/byte caps. Then a prospective independently reviewed source/protocol could be considered as a distinct whole-observable feasibility experiment. No benchmark is part of the proposed current scope. This memo neither selects nor freezes its architecture, constants, data, budgets, controls or launch. All coordinate, wake-slice, receiver, CPU usefulness, R8 and earlier temporal/physical limitations retain their existing status.
