# Static proposal: one synthetic return through the existing automation channel

Status: engineering direction only. This document allocates no invocation, source execution, browser launch, saved review, timing campaign or scientific successor. No campaign is modified. Adoption would require its own prospective protocol, independent source review, freeze, publication and exact remote verification, plus whatever authorization and time window apply then. The original `2026-10-15T23:00:00Z` new-launch cutoff is unchanged; this proposal cannot extend it or spend a terminal budget.

## The narrow question

Can one fresh 3,840-byte ordinary heap payload, constructed in the controlled page, be returned as a bounded plain JavaScript number array by one Playwright `page.evaluate` call, validated by Node, written to one exclusively created evidence file, and independently reread byte-for-byte after external process closure?

This would examine a different evidence path already used for page automation. It would make no application data-transfer HTTP request, start no HTTP evidence sink, grant no browser permission, and change no browser security flag, enterprise policy, origin or permission setting. Locally fulfilled fixture navigation/resource requests remain distinct from payload transfer. The browser's Local Network Access restriction would remain in place. The automation session already has authority to inspect its controlled page; returning that page's synthetic bytes to its owning Node process does not require a page-to-loopback fetch.

The preceding transport result is immutable. In the new diagnostic's saved trace, `e24` is a non-warning `CorsIssue` carrying `LocalNetworkAccessPermissionDenied`, and `e29` is `Network.loadingFailed` for the same normalized request ID (`cdp-5`) with the same CORS category and `net::ERR_FAILED`. The reserved-sink URL label and transfer ID correlate those observations to the one new fetch. The Node sink recorded zero request entries, including zero OPTIONS and POST entries. This is evidence about that new synthetic fetch. The earlier scientific fetch did not retain equivalent causal evidence; its cause is still unresolved.

The source records examined here are the new diagnostic's `results/result.json`, `results/capture.json` and `raw/trace.public.ndjson`, bound to source commit `fe2c19a30b4605ec755e8e7103946d7ef037a76a` and source freeze `3a2f596279d7720ad16ca4eb07685061ecb54769c6c86867750d23d75327d7d8`. The coordinator reports the actual capture exited 0 and completed. This proposal does not substitute for the separately reserved saved-evidence review or claim its outcome.

## Proposed fixed condition, if adopted separately

Retain Chrome 155.0.8059.80, Playwright 1.62.1, explicit headless executable and fresh browser/context, the same fixed page origin and exact route-delivered local source mechanism. A new minimal page would contain no GPU APIs, shader, scientific input or earlier raw output. All new source would be standalone. Runtime and source admission would remain bounded and independently bound to the new freeze.

Use the same non-scientific byte fixture for comparability: length 3,840, byte i equal to `(73*i+19) mod 256`, SHA-256 `b92773fc3edb949a8a0d6e4a2f60ef2020ee2bd5bf6f8299c1448142a6cd3404`. Freeze a new campaign-local copy of its exact binary and descriptor. The browser constructs its own ordinary `Uint8Array`, then deliberately copies it to a dense plain array using the fixed implementation. The host must never construct the received-output file from its expected fixture or regenerate replacement bytes after a failure.

One payload-bearing evaluate call would return an allowlisted envelope: format/version, fixed payload ID, declared byte length, the plain array of values, final construction phase, and observed page origin and secure-context state. Its actual page observation must remain unknown if no return is received. Source bindings and the frozen served page establish the implementation identity; an echoed payload ID or source label by itself proves no byte integrity.

A plain array is chosen explicitly to avoid assuming that this Playwright version serializes a `Uint8Array`, `ArrayBuffer` or remote object handle as a binary byte stream. The diagnostic tests this specific array representation. It should not switch to base64, a handle, a binding, console output, screenshots, files, another evaluate call or another transport after observing the result. Those would be separate designs requiring prospective adoption.

Before conversion to a Node Buffer, the receiver checks the exact envelope keys, correct version/format, exact length, a dense array with all 3,840 elements present, and each element's type, finiteness, integrality and range 0–255. It must reject floats, negative or oversized values, nulls, holes, unexpected keys and wrong lengths. `Buffer.from` must not be used as a validator: its coercion/truncation behavior can conceal an invalid representation.

Only the successfully validated returned values become the received Buffer. Compute a digest of that actual Buffer, open a new output file exclusively, and write its bytes with explicit handling of partial writes. Account for bytes actually written, close the file and retain any partial file after an error. Record actual length/digest separately from whether they match the expected fixture. A completed declared-length write can contain the wrong bytes; it must never imply fixture equality. No overwrite, retry, regenerated fallback output or deletion of partial evidence is permitted.

Independent saved review happens only after the external lifecycle is terminal. It rereads the actual file and the separately frozen fixture without importing the producer, and checks exact byte equality in addition to length and SHA-256. Close plus reread establishes the resulting file contents in this observed system state; it is not a claim about power-loss durability or crash-safe storage.

## Evidence needed before making even the narrow claim

|Evidence|Required distinction|
|---|---|
|Source/runtime binding|New source inventory and freeze, exact fixture, actual browser version and pinned runtime, exact served source bytes. No scientific or old-output imports.|
|One-shot authority|Permanent terminal invocation lock, at most one browser lifecycle, exactly one reserved payload-bearing evaluate attempt if reached, no fallback extraction, application-fetch count zero by static source plus available observations. An interrupted call remains consumed.|
|Prearmed local observation|Host phase recorder and browser/page failure events ready before the evaluate call. A host `evaluate-started` record precedes invocation; `evaluate-returned` exists only after its promise actually resolves. Browser execution or last phase remains unknown if the call fails before returning.|
|Returned representation|Actual decoded API result preserved under a strict retained cap, representation version, array length and validation checks. This is the value Playwright delivered to Node, not a capture of its internal wire protocol or proof of its encoding.|
|Received bytes|Buffer derived only from the validated returned array; its actual digest and byte length, distinct from expected-fixture comparison. Preserve evidence when shape is valid but content is wrong.|
|Exclusive persistence|One exclusive-open attempt, successful write counts/bytes, close outcome, actual partial or full file identity. An API result is not proof of a file write.|
|Independent final bytes|After external closure, independently read file length, digest and exact equality to the frozen fixture. A producer receipt alone cannot satisfy this gate.|
|Lifecycle/accounting|Actual caller completion and exit, bounded whole elapsed time, complete owned-process closure and reaps, registry provenance, pipe/file lengths, combined raw/private/output accounting and sampled RSS. A timed-out evaluate or closed page cannot certify detached Chrome cleanup.|
|Privacy and trace integrity|Selected raw exceptions/identities remain private; public derivative has explicit allowlist, stable event IDs, separate clock domains, trace limits and loss/error counters. No profile, PID, private path or unrelated page data in public artifacts.|

For a concrete future proposal, the previous diagnostic's 60-second external allowance, inclusive 40-second worker limit, cleanup through 58 seconds, 8 MiB combined retained-output cap, 2 GiB sampled owned RSS cap and 2,048-event cap are conservative ceilings worth retaining. They are suggested constraints here, not newly available allocations. The single evaluate round trip could have a prospective 10-second host deadline with an earlier worker work stop to preserve cleanup time.

An evaluate timeout needs its own cancellation semantics. `Promise.race` timing out does not cancel browser JavaScript or prove its serialization stopped. The design must stop further work, close the owned context/browser and, if necessary, use the independently verified ownership supervisor for cleanup. It must not issue a second extraction to discover whether the first might have succeeded. Missing return, ambiguous cancellation or uncertain ownership is incomplete evidence. A transfer's actual last observed phase must not be overwritten by a generic terminal state.

A retained canonical JSON copy of the decoded primitive-array envelope can be capped at 32 KiB, with the received binary capped at 3,840 bytes. Values alone have at most 15,361 characters in ordinary compact JSON (`[255,...]`), but this bound describes that saved diagnostic representation, not Playwright's actual protocol traffic. Reject a decoded envelope that violates its bounded shape before retaining it; declare omitted/oversized error evidence explicitly. All retained representations, partial binaries, logs, locks and final receipts count toward one combined cap.

## Decision and rejection rules

1. **Narrow positive observation:** source/runtime/attempt bindings hold; the evaluate call returns a valid bounded representation; its received Buffer matches the fixture; exclusive persistence completes; independent post-closure reread matches exact bytes; instrumentation, lifecycle and output accounting are complete. Allowed claim: this one synthetic heap fixture reached Node through the existing automation API and was retained exactly once under the recorded condition.
2. **Serialization/API boundary failure:** evaluate rejects, times out, returns a remote/unserializable or invalid value, or fails shape validation. Preserve the error category and last observed host phase. Do not infer that browser construction failed merely because Node received no result.
3. **Wrong received content:** shape is valid but byte equality/digest differs. Preserve the returned value and still persist its actual bounded bytes through the one exclusive write path; classify content mismatch. Do not repair bytes from the expected fixture. Correct file persistence of wrong bytes remains wrong content.
4. **Persistence boundary failure:** valid returned values exist but exclusive open, write, close or independent reread fails. Preserve actual partial bytes and counters. Do not relabel this as a control-channel serialization failure.
5. **Protocol deviation or incomplete evidence:** any extra payload extraction, browser relaunch, HTTP fallback, permission/security change, scientific import, cap breach, truncation, observer error, source mismatch, unknown final ownership, missing actual external completion or incomplete accounting makes the overall diagnostic inconclusive/rejected. Narrow raw observations may still be reported with their limitations.

The saved reviewer must keep the observed transfer outcome distinct from whether the evidence is internally consistent. It should compare explicit shared projections rather than whole differently wrapped objects. It must also separate declared-length completion, digest of actual bytes, expected-fixture equality and host persistence; none substitutes for another.

## What this path sacrifices and cannot establish

It would no longer exercise browser fetch, CORS/preflight, Local Network Access admission, a network response acknowledgement or the Node HTTP sink. Therefore it would not show those mechanisms are repaired or usable, and it would not contradict the recorded denial. Returning through the automation interface is an intentional engineering change to the output path.

It would only show one heap-backed value transfer through this pinned automation stack. It would not identify the earlier scientific failure's cause, validate an earlier missing output, establish a failure rate, demonstrate general transport reliability or authorize a scientific successor. The periodic test fixture verifies this exact byte sequence; it is not exhaustive testing of arbitrary encodings, sizes or transformations.

No GPU buffer is mapped. The design does not test WebGPU mapping completion, mapped-range lifetime, copying before unmap, device loss, GPU-to-CPU synchronization or whether the earlier fetch body had a lifetime issue. If a future authorized GPU design needs this output path, it would need a separately reviewed lifetime contract: materialize an owned ordinary heap copy while the mapped range is valid, then release GPU resources at explicitly defined points. This proposal supplies no permission or evidence for that future design.

The automation channel becomes part of the evidence and trust path. Returning values depends on Playwright/CDP serialization and its controlled-page execution context, and may share scheduling and transport resources with instrumentation. Host receipt is an acknowledgement to the Node orchestrator; there is no separate page-visible HTTP acknowledgement. Those differences must be reflected in later scientific I/O accounting rather than presented as an interchangeable zero-cost replacement.

## Scaling and timing remain a separate question

The representation introduces at least a deliberate browser heap-to-array copy, protocol serialization, host deserialization to a number array, conversion to a Node Buffer and file writes. Number arrays and textual/protocol wrappers can occupy substantially more memory and wire space than the original bytes. Exact amplification depends on the pinned serializer/runtime and cannot be inferred from `byteLength`, the compact saved JSON size or one small successful sample. Avoid claiming zero-copy transfer or extrapolating a 3,840-byte result to a larger readback.

Any later performance question needs its own prospective fixed synthetic sizes, repetition/warmup policy, resource caps, source/runtime freeze and interpretation. It must measure the chosen representation's end-to-end impact separately before including it in a scientific throughput claim. No timing sweep or repeated sample is allocated here.

A host monotonic interval around the evaluate call includes scheduling, browser execution/conversion, protocol serialization/transport, host deserialization and delivery. A browser-local interval around payload construction and array conversion covers only that local work. They are different clocks; subtraction does not isolate an exact wire time. Record host-side validation/Buffer conversion, exclusive write/close and independent reread separately using the host clock. If finer serialization attribution is later required, it needs dedicated supported instrumentation and a new design. GPU computation, GPU readback and this changed evidence-transfer cost must remain separately identified; a future performance comparison must include or explicitly exclude them consistently on both paths.

Recommended next decision: preserve this as an unallocated engineering option. If a further diagnostic is authorized within an applicable time window, review and freeze the smallest one-shot heap-only implementation and its saved checker before invocation. A positive result would support selecting a candidate evidence path for further design, not a numerical or physical conclusion.
