# Current-geometry bound: independent source and interface challenge

Desk checkpoint: `research/m31-current-bound-design-2026-10-16`. This is a source/prose and symbolic review, not implementation permission or experimental evidence. Exactly 9 existing content files were inspected, below the 14-file limit, plus the 3 new drafts. No raw swarm arrays, scientific imports/evaluations, fixtures, solver calls, browser launches, timing, historical reviewer reruns, external retrieval or new agents were used. The prior disclosed result exposure remains historical context; its raw artifact was not reopened here.

## Recommendation

Accept the draft as a conditional exact-real current-geometry construction worth developing. Do **not** call it a certificate for the existing native JavaScript query. The present blockers are an unresolved numerical target and an unresolved returned-output contract, followed by the branch/admission/resource obligations below.

The defensible operational direction is an explicitly named, separately requalified mathematical-model query that returns loads plus certified error/enclosure information for the **complete current coupled model**. Every comparator must implement that same query. Its implementation may omit individual positive coefficients only when their contributions remain included in the complete enclosure. Keep the original legacy-query compatibility question and the broader physical/live-flight research objective open; a certificate for this newly specified mathematical model is an intermediate result, not completion of those goals. If native legacy equality is instead mandatory, retain it as the primary contract and require an actual primitive/rounding/branch bridge before calling any omitted native work certified. Nothing read here supplies that bridge.

This recommendation does not silently adopt the draft's model boundary. An adopted note must explicitly name the target, preparation/constants/normalization choices, changed output obligations and remaining legacy discrepancy question before any executable protocol is frozen. No fresh measurement is authorized by this note.

## 2. Keep four reference objects distinct

| Object | What fixes it | What the current draft establishes |
|---|---|---|
| Current state/preparation | Original binary64 states, operation ordering, prepared axes/offsets, rounded receiver point additions and declared constants | Conditional bounds start from supplied prepared values. They do not yet enclose preparation or reproduce every native geometry-validity test. |
| Exact-real geometric model | Exact interpretation of declared endpoints/constants, full branch definition, exact positive nominal sums and normalized weights | The node argument can enclose this model, under its stated admission and outward-arithmetic premises. |
| Legacy assembled numerical model | Actual native branch results and rounded K/a/S0 from the unchanged builder | No bridge is supplied from ideal geometric bounds to all values/classifications this native program can return. |
| Legacy returned query values | Ascending-source rounded reductions, 56-step roots, rounded thrust totals/divisions/square roots and residual pass | The corollary concerns an exact fixed point, not automatically these finite-program values. |

Specific source-to-math gaps must be named, not hidden behind “same formula”:

1. The exact-real identity `spread*(h-origin*D)` equals the source's `spread*(h/D-origin)*D` algebraically, but the source uses the latter floating grouping. Its attenuation argument `(radial/D)/(spread*(normalizedDown-origin))` and fade argument `radial/halfWidth` are likewise equal in real arithmetic, not guaranteed bitwise equal. A native enclosure must follow or bound the actual evaluation graph.
2. Constants such as D, induced, area and sqrt2minus1 originate in rounded products, Math.PI and Math.sqrt. Freeze whether the target constants are exact rationals represented by the resulting binary64 values or exact evaluations of declared mathematical expressions. Those are different models. “Declared positive constants” alone is not a complete numerical specification.
3. Legacy S0 is a left-to-right rounded sum. `nodeMap` forms rounded `total += f0*x` and `sqrt(total/S0)`. The corollary requires exact weights `f0/exactSum(f0)` summing to one and candidate-derived exact weighted square roots. Replacing them with independently rounded weights, a rounded source amplitude or the legacy rounded denominator does not inherit the corollary as written. In particular, the exact-real sum of `f0/S0_rounded` need not equal one, so the proof's unit source cube cannot simply be assumed.
4. Legacy a is itself rounded after the K multiplication and two square roots. A node bound on exact K times exact beta/nu is not automatically an enclosure of the rounded a array. The complete branch/normalization arithmetic and outward errors must be included.
5. Preparation checks Math.hypot for quaternion/axis/offset norms; center/radial branch decisions also use it. An ideal square-root norm enclosure is not a guarantee about an omitted native Math.hypot return. The prior finite pinned Chrome equality result does not provide a uniform error bound for that primitive. The same discipline applies to every other nonbasic primitive needed by the proposed numerical proof.
6. The exact fixed point and a high-precision numerical reference must be distinguished. A tight approximate reference is not an exact oracle; its own rigorously bounded numerical uncertainty belongs in a certificate check. Comparing to legacy outputs should separately report preparation, coefficient/branch, normalization and finite-solve differences to the extent they can be separated, without redefining a disagreement as certificate success.

The draft correctly avoids assuming exactly unit axes. Preserve `e=d-(d·a_j)a_j` using actual declared axes; the orthogonal-projection distance identity is not licensed by near-unit tolerances. Its common shape bound is a valid conditional upper-envelope pattern when all supplied interval premises are sound. This review does not claim useful width or useful traversal complexity.

## 3. Branch, admission and rejection obligations

The active formula is only one branch. `lean-anchor.cjs:101–151` and `reference-excerpt.cjs:5–35` impose this order:

| Stage | Existing outcome and boundary | Required node treatment |
|---|---|---|
| Self | i=j is excluded before pair classification | Remove exact membership. Geometric coincidence is not self identity; duplicates remain separate vehicles. |
| Center guard | Nonfinite native center, center>512, or max absolute center component>257 gives invalid symbol11 for all four rotors | Discharge this before a center-neighbor zero. A real-far center alone is insufficient. |
| Center support | Center>=neighbor (3) leaves zero symbol1 | A group may be omitted as zero only with all earlier guards and the chosen target's cutoff comparison proved. |
| Rotor displacement/down guards | Nonfinite or component>258, nonfinite down or absolute down>1024 gives invalid11 | Must not disappear under an aggregate with a small upper contribution. |
| Down support | down<=0 gives zero2; down>=downCut gives zero3 | These return before radial computation. Do not require later branches for these proven exits, or reorder their error semantics. |
| Radial guard and near field | Nonfinite radial or radial>2048 is invalid11. For 0<down<minDown*D, radial<nearRad gives unsupported4; otherwise zero5 | A node crossing the near slab needs branch-specific proof/refinement. Projection zero or a tiny active-formula bound cannot bypass unsupported4. |
| Width and radial cutoff | Nonpositive/nonfinite halfWidth is invalid11; radial>=radCut*halfWidth gives zero6 | Preserve comparison inclusivity and the prior width guard in the chosen numerical target. |
| Projection/speed | Projection is max(0,dot); nonfinite projection or speed outside finite[0,128] is invalid11; projection<=0 gives7, positive speed8, otherwise9 | Zero projection is a late classification, not an early admission bypass. Exact-real positive terms can round/underflow to native zero; support/class counts therefore belong to the target choice. |
| Positive term accounting | Immediately append/count a positive term, then throw on count>2,000,000; then check nominal-scaled cap | Resource failure is separate from model zero/rejection. Do not silently truncate or defer the cap past later work. |

Global geometry and nominal diagnostics remain significant even for pairs screened as far. The source checks all state components for finiteness, quaternion/axis/offset tolerances, nominal positivity and finite nominal totals. It accumulates admission reasons in the order geometry, nominal, near-field, invalid-term, scaled-cap. The builder does not simply stop at the first bad input; it can encounter a positive-count throw before returning its aggregate rejection. A new Boolean-only rejection API can be legitimate only if explicitly adopted for all comparators, not described as preservation of exact legacy rejection diagnostics/failure order.

Use at least these distinct dispositions: **proved admissible**, **proved domain rejection**, **unresolved numerical/branch certificate**, and **resource failure**. An upper bound above a cap is uncertainty, not proof of a violating term. Refine or perform a charged exact fallback; do not relabel uncertainty as physical invalidity or remove that case from a performance denominator. If the operational contract requires rejection reasons/counts to match the legacy path, unresolved or mixed nodes may force extensive classification work. A uniform proven branch can sometimes be counted in bulk; the contract must say what evidence makes that count exact.

### Caps, graph and order

- Both unscaled K<=128 and whole-source-domain scaled K*beta<=128 matter to the draft's chosen guarded model. Proving them at a candidate yhat alone is insufficient. The draft's use of a node-wide beta upper bound is a conservative sufficient condition, provided the arithmetic is outward and the source domain is really established. It may force refinement without proving any actual violation.
- The two-million budget counts actual positive rotor-source entries, not retained entries, visited nodes, unique vehicle edges or coefficient multiplications. For omitted nodes, keep sound positive-count lower/upper information. A possible-positive upper count below the limit may certify safety; an upper count above it does not prove failure. Exact counted diagnostics or the native first-overflow location may require refinement in original receiver → ascending source → rotor order.
- `schedule` uses descending center z and ascending ID ties; graph eligibility checks every positive source edge against that key. Equal-height edges are allowed only from smaller source ID; `heightViolationEdges` is a separate diagnostic and is not itself the solver's rejection predicate.
- The conditional nonnegative algebraic fixed-point result and the current ordered solver's admissible domain are different. The theorem does not itself justify silently accepting cyclic/out-of-order inputs in an interface whose solver rejects them. Conversely, declining difficult nodes without fallback must remain an explicit unsuccessful outcome, not a hidden domain restriction.
- A node containing a potentially out-of-order source cannot be accepted merely because its aggregate contribution is small. Prove those members zero, refine them, or handle the input under the declared rejection/fallback rule. Use current source IDs/membership, disjoint row partitions and exact self removal.
- Spatial tree traversal order is not native ascending-source reduction order. Reassociation, sorted-cell order, parallel sums or aggregated positive terms change rounded alpha/residual values unless an independent equivalence proof exists. Exact-real interval summation can legitimately use another order under a new numerical contract; it cannot simultaneously claim unchanged native output bytes.

## 4. A rigorous operational target to adopt explicitly

A concrete prospective specification can use the following two tracks without substituting one for the other:

**Legacy compatibility track.** Keep unchanged L/F, their complete native return/rejection semantics and historical timings intact. The desired statement remains explicitly named: equality with, or a certified error relation to, that guarded binary64 program on the full declared current-input domain. No current-node geometric theorem satisfies that statement until preparation/constants, norm/branch decisions, scaling/reductions and finite root-return uncertainty have a sound bridge. Finite discrepancy comparisons later supply observations, not a uniform proof. If exact legacy CSR and residual outputs remain mandatory, retain their cost and constrain the new method accordingly.

**Mathematical-model certification track.** Define a named model M-current over current inputs, not stale matrices or solely the three historically successful states. Freeze the preparation boundary; the exact interpretation of every supplied constant; guard/cutoff precedence and inclusive boundaries; exact positive nominal sums/normalized weights; complete finite nonnegative coefficients; self membership; caps and declared order domain. All omitted contributions belong to M-current even when never separately materialized. Specify a sound outward arithmetic system with a justified norm/square-root policy; “one nextafter” around an unqualified native result is not a substitute for such a policy. On uncertain branches or arithmetic, refine/fallback or return an explicit unqualified outcome.

For M-current, a complete query should return at least: input/model identity and status; candidate rotor ratios and physical-unit load outputs; guaranteed rotor/load/body-force/moment intervals or declared error bounds covering the complete model; the requested normalized quality decision; and sufficient current partition/admission/cap provenance for independent checking. The exact reference and its numerical uncertainty must be independently specified. Candidate-derived source amplitudes must enclose the exact weighted square roots, and current beta/yhat aggregates must be rebuilt whenever the candidate changes. Hierarchy construction, any candidate solve, every reaggregation/refinement, certificate propagation, fallback and output consumption belong to query cost.

This is a change from returning exact coefficient arrays and a complete exact-style residualMap. State that change prominently, justify how certified loads serve the original research objective, and preserve a separate qualification interface for full symbol/coefficient/reference inspection. Do not require the approximate method to produce less than its competitors, or require competitors to produce old diagnostics that the approximate method omits. Do not interpret an M-current certificate as a certificate for legacy Math.hypot or as physical wake validation. The overall research goal remains active until its original model/physics/live-use requirements are independently addressed.

### Comparator fairness under the new interface

| Comparator | Fair obligation |
|---|---|
| F-derived complete query | Requalify the existing screening strategy for the explicitly chosen target and new output interface. Its native code is not automatically a rigorous M-current reference. Charge all current preparation, admission, solve and required certificate/output work. |
| Exact hierarchy H | Build/refit the same current hierarchy under a frozen policy; prune only proved zero support, otherwise resolve exact-target terms/reference intervals. Preserve every required positive contribution and rejection. H is not a cached sparse answer or an excluded preprocessing stage. |
| Bounded-omission method | Use current-node contribution enclosures and an independently accounted candidate; satisfy the same returned accuracy/status contract, include all omitted positive contributions, and pay all failed/refined/fallback work. No free full comparator solve or prevalidated admission oracle inside candidate setup. |

Keep required scientific semantics common while permitting truthful method-specific work counters. Exact diagnostic counts, CSR output, graph materialization, ordinaryLmax, full residual-map fields and checksum inputs must each be marked required or omitted in the common interface before execution. Requalified timings form a **new experiment**; the closed Chrome totals are historical context, not denominators for a method performing a changed task. Different preparation/output/certification boundaries cannot be repaired by subtracting estimated old phase costs.

A future prospective protocol must retain all prescribed inputs and failed/unresolved outcomes, freeze error tolerances and independent reference uncertainty, use common current-input ownership and cache rules, define deterministic traversal/refinement/candidate construction, budget worst-case singleton fallback, and prohibit tuning against the scored cases. The draft proves neither fewer visited nodes nor speed nor useful enclosure width. No priority/novelty conclusion follows from this source review.

## 5. Concrete blockers and resolutions for ADOPTED-DESIGN

| Blocker | Resolution needed before executable qualification |
|---|---|
| “The target” can mean prepared real geometry, rounded coefficients, or returned native loads | Name M-current and/or the legacy program explicitly; freeze preparation/constants/weights; maintain a separate bridge/discrepancy obligation. |
| Ideal norm/shape bounds are mistaken for native Math.hypot enclosures | Supply a verified quantitative primitive/evaluation-graph bridge, or limit the certificate explicitly to the newly adopted mathematical model. |
| Omission suppresses unsupported/invalid/cap/order outcomes | Freeze the branch state machine and tri-state proof/refinement logic; preserve resource failure separately; pay complete fallback. |
| Current exact CSR/residual/diagnostic contract conflicts with omitting positive coefficients | Keep and pay those outputs, or adopt one common certified-load interface for F/H/bounded method and requalify all timings. |
| Candidate/amplitude/normalization rounding invalidates the defect premise | Enclose exact candidate-derived weighted square roots, current beta and nu, the complete contraction and defect evaluation; account for reference uncertainty. |
| Hierarchy/count/order work is treated as free or stale | Include current build/refit, membership, self removal, positive-count and ordering proof, candidate-dependent aggregates, refinement and failure work in complete-query timing. |
| Conditional proof is presented as original-goal completion | Mark this as an intermediate mathematical certification stage; retain native compatibility, physical validity, long-flight/live behavior and broader feasibility as separate unresolved goals. |
