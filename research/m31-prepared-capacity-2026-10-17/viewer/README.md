# Existing-cap capacity viewer

Source preparation only until the parent signals terminal scientific results.
The app initially has an UNBOUND identity and cannot render any geometry. The
viewer is excluded from the scientific source freeze. Its later binding pins the
actual new result index, three case records, three complete profiles, renderer
and existing vendored Three.js modules. It never imports a scientific module.

The default view is the dense180 static grid. Sparse180 is another static
regression fixture; fresh-a64 is a saved final state from local 3D Boids with
airflow off. Labels and the original replay link preserve that distinction.
Colours, source-centre boxes and positive-support lines use the new saved
coverage only. No force vector, wake volume, animation or trajectory is invented.

The previous renderer is reused with a bounded180-instance pool and actual
per-scene instance counts. Poses, quaternion display, enlarged3× drone glyphs,
orbit and proof-box rendering are otherwise unchanged. The prior responsive
stylesheet is retained with small additions for flags and profile tables.

Complete preserved accuracy qualification gates the geometry. A practical-hurdle
miss is shown separately and still permits display of qualified saved records.
The global hurdle includes the final process-lifetime RSS; selected-case RSS is
the recorded after-case lifetime high-water mark. Neither is a per-scene memory
delta or hard OS cap. Profiled time includes cProfile overhead; cumulative times
overlap, and the viewer never sums them. Only recorded non-overlapping outer
stages are shown as a stage table.

The64control matched a whole prior reference record. The180states matched exact
independent roots/signed-load endpoints and complete positive support; containment
inside old96-bit coefficients is explicitly distinguished from unavailable
independent192-bit pair equality. The old native1e-8 status is unchanged.

Browser plugin is not available in this session. Later UI-only validation uses
installed pinned Playwright/Chrome after the parent's terminal-results signal,
with at most two120-second attempts and preserved failures. No server restart;
the existing127.0.0.1:8876 service remains unchanged. The flow is load -> select
case/receiver/rotor -> verify actual saved positions, coverage and cost -> toggle,
orbit and reset. Source preparation is not rendered QA and is not a pass claim.
