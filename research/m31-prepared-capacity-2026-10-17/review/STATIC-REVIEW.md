## Stable IDs, ordered endpoints and the coefficient claim

For each 180 case, the driver requires equal scene IDs, equal saved raw-input
digests, exact ordered raw-input equality, and duplicate-rejecting stable-ID raw
maps. It selects exactly the two unique method names `hierarchy` and `filtered`.
Both complete prepared maps must match the new prepared map; both saved result
objects must be exactly certified loads, tolerance achieved, with no witness.

The saved producer solve objects contain `bisections`, `candidate`, and
`iterations`, with no saved traversal-order field. A direct old/new solve-order
comparison is consequently unavailable and explicitly recorded as unavailable.
The current frozen tree still defines and uses its canonical solve order; the
review does not manufacture an old order from a different candidate schema.

The entire new `{id, roots, loads}` row is compared by unique stable ID to the
saved `independentReference` row. The reviewer confirmed that both saved
reference lists and both saved prepared lists have the original input ID order.
The unchanged wire emits load rows in that same current input order. Inside
each row, equality retains all ordered lists and exact numerator/denominator
strings: four roots, four rotor loads, collective load, three world-force and
three world-moment intervals. Mapping rows by ID therefore does not erase rotor
order or endpoint association. Missing, additional, duplicate or changed
reference rows and nested endpoint fields cannot qualify.

The old independent records explicitly specify coefficient/source bits 192 and
128 root bisections. Their complete roots and signed loads are valid saved exact
equality targets. They do **not** contain a 192-bit pair-coefficient table.
The new driver correctly refuses to label the coefficient comparison as
independent-192 equality.

Old producer certificate receiver/source fields are input-array indices. The
driver checks their integer ranges and translates through the saved input's
stable-ID list; it does not assume a numeric relationship between an ID and its
index. Positive entries alone form `(receiver ID, rotor, source ID)` keys,
with duplicate keys rejected. Source inspection of the frozen tree confirms
that new pair `i/j` are taken directly from `ids[ii/jj]`, with scalar records in
canonical receiver/rotor/source order. New positive keys must also be unique.

Saved-only reduction confirmed that the two producer maps are exactly equal:
3,056 positive keys for dense180, zero for sparse180, with no duplicates.
The new support must equal both old supports. Each new rational interval must
satisfy, exactly with `Fraction`,

`saved96.lower / 2^96 <= new192.lower <= new192.upper <= saved96.upper / 2^96`.

This is exact rational containment, not tolerance agreement, floating rounding,
or the unavailable independent-192 pair equality. Sparse containment is vacuous
because its required positive support is empty; its complete zero-load/root
equality and coverage gates remain mandatory.

## Profiling privacy, observation boundaries and failure preservation

There is one standard cProfile instance per actual regeneration. InputHelper
construction is outside the profiled call; no timing calibration, warmup or
repeat is introduced. The serializer retains every function record and caller
edge. CPython 3.12's source confirms function rows use primitive/total counts,
while caller tuples use total/primitive counts; the final JSON labels preserve
this distinction. Caller keys are records constructed by the same cProfile
snapshot. Function IDs preserve distinct records even when basename
sanitization yields matching display names.

Repository absolute filenames become repository-relative names; external
absolute filenames become basenames. Original private paths are not output,
nor is a raw `.prof` file published. Exception trace locations use basenames;
arbitrary exception messages are replaced by a bounded generic reason. Complete
profiles may be large, so file and aggregate output limits include profiles,
journal, STARTED and result files. Cumulative times explicitly overlap and must
not be added as disjoint phases. Profiler overhead remains in the observation.

Separate outer monotonic phases cover setup, baseline loading, regeneration,
profile serialization/write, complete-wire serialization/write, saved
comparison and closure verification. The final wall/RSS fields explicitly end
before final index serialization and stdout. They are not completed-process
wall measurements. macOS `ru_maxrss` is in bytes and is a process-lifetime peak,
including earlier cases and loaded baselines, not a stage allocation, delta or
OS memory limit.

The observed hurdle is each profiled call at most 60 seconds and sampled
process-lifetime RSS at most 1 GiB. Accuracy and capacity flags are separate.
An accurate result can fail the capacity hurdle; the explicit outcome records
that negative practical decision. Exit zero means completed accuracy
qualification, so consumers must read the capacity field as well. Neither
field establishes production speed, large-scale extrapolation, physical
validation, new native qualification or publication-level novelty.

Complete profiles and returned scientific wire records are exclusively saved
before outcome assertions. If a regeneration raises, its partial profile is
preserved where the remaining time/byte budget permits, and no later scene is
attempted. An exception or mismatched comparison consumes this allocation.
Per-file evidence is bounded to 32 MiB and aggregate new evidence to 256 MiB.
