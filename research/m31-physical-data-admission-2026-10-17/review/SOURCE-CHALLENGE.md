2026-10-17. Independent source-only review. **The records can support a bounded provenance/data-quality admission audit; they are not yet an identified force-label reference for the current model.** Resolve the clock, acceleration convention, mass, calibration and lag associations before defining any later physical comparison. This review makes no physical-validity, model-ranking or novelty conclusion.

Only previously retained source text, repository metadata and the retained paper text were read. Git blob identities were checked from bytes using the Git object-header rule. No third-party code was imported/executed; no additional material was downloaded; no data was fitted/scored; no scientific calculation or frozen-package edit was performed. Source behavior below describes the inspected code/default path, not proof that a historical training run used that path. In particular, `training.py` lines 22–30 permits precomputed arrays to bypass preprocessing.

## Concrete blockers and limited inferences

**1. Labels are model residuals, not direct interaction-force measurements.** `utils.py:160–195` forms total thrust from four PWM/voltage polynomial predictions, rotates it with the quaternion-derived body-z axis, and subtracts it from a mass-times-acceleration term. The default selected by `training.py:49` is the delayed variant using the interpolated acceleration columns. The conversion source identifies those columns as onboard `stateEstimateZ` acceleration (`convertData.py:76–78`); the inspected code does not establish whether they are inertial acceleration, gravity-inclusive specific-force estimates, or which firmware convention was used. The IMU-labelled branch adds no explicit gravity term, whereas the numerical-differentiation branches do. Resolving that convention is necessary before reconstructing a physical residual.

The five-point derivative is computed from interpolated velocity (`utils.py:108–111`) and has separate filtered/smoothed branches, but those are not the inspected default `fa_delay` target. Paper §VII-B describes five-point numerical differentiation and delay compensation. Preserve this code/paper association gap rather than silently selecting the branch that best agrees with the current model. `utils.py:215,230` converts newtons to gram-force-equivalent targets; `:435,437` selects only the vertical component for learning. Logged motor-force/torque columns and a three-component intermediate residual do not establish independently measured rotor forces, collective load, signed world-force vectors or moments.

**2. Timestamp units and synchronization require direct admission checks.** `convertData.py:69,114` retains the raw tick while describing it/header-labelling it as milliseconds. `utils.py:57–59` subtracts each file's own first tick and divides by one million. Paper §VII states microsecond onboard clocks, preflight broadcast synchronization, roughly 10 ms logging, and negligible drift for its short flights. The code and paper support microseconds as a plausible interpretation; a CSV header alone cannot settle it.

Independent zeroing of each robot's first record discards the original inter-robot start offset. Paired files are then resampled to common zero-based times (`training.py:120–143`). This does not prove that same-index observations were physically simultaneous. Retain raw first/last ticks, ordering, duplicates, gaps, common-clock overlap and relative starts in the four-file audit; distinguish numerical overlap from demonstrated sensor/estimator/actuator synchronization. The inspected files do not quantify inter-signal delays, residual clock offsets or drift.

**3. Quaternion use needs a convention and interpolation audit.** Conversion decompresses quaternion components and declares x/y/z/w order (`convertData.py:10–30`); `utils.py:18–51` is consistent with that ordering and uses the rotation matrix's third column as the thrust axis. However, `utils.py:78–80` defaults to linear interpolation despite the function name, and `:113–119` interpolates each quaternion component directly. There is no sign-continuity correction, renormalization or spherical interpolation in this path, nor an arcsine-domain clamp. Even valid endpoint quaternions need not yield a unit quaternion after component interpolation. This is a source-level risk, not an observation that the selected files contain such a failure. Audit raw norms/sign changes and preserve the original convention; do not normalize or repair records silently. A single position marker, as described by the paper, is not independent motion-capture attitude ground truth.

**4. The 32 g/34 g mismatch changes the residual.** `training.py:712` uses 67 g for the large vehicle; `:733` uses 32 g for the small vehicle. Paper §VII/Table I and §VII-B report 34 g and 67 g. The collection README establishes platform/calibration families but does not resolve the mass discrepancy. It could reflect configuration or version differences; this review cannot choose a cause. In the default branch, changing mass changes every residual by the mass difference times the recorded acceleration; it is not merely a reporting-unit change. Preserve both source statements and require a per-run mass/configuration association before label reconstruction. Do not choose 32 g or 34 g by agreement with a prediction.

**5. Calibration evidence has narrower scope than force-label accuracy.** `system_id.py:22–27` restricts PWM to a stated range, normalizes PWM/voltage, and divides a whole-vehicle force reading by four. The paper describes identical PWM on all four motors during upside-down load-cell calibration. This supports a nominal per-rotor polynomial inferred from collective bench measurements, not separately measured rotor loads in interacting flight. The five small-vehicle coefficients in `training.py:735–739` match the retained `defaultcf.txt`; that is a useful provenance connection. It does not establish each airframe/battery/date's calibration uncertainty or extrapolation behavior.

`system_id.py:112` passes the identical two files for fitting and “validation.” Consequently, this entry point's validation labels do not designate independent held-out calibration data. The retained coefficient file's fit score supplies neither an independent error bound nor a transferable flight-force uncertainty estimate. Calibration file identity, vehicle mapping, units, PWM/voltage domain and independent residual uncertainty remain requirements for any later quantitative use.

**6. Lag treatment assumes timing and crosses merged-flight boundaries.** `utils.py:170–174` implements a fixed 0.16 discrete first-order thrust update, using the previous desired-thrust sample and one initial value. Its nominal 100 Hz grid (`:84`) corresponds to the Euler coefficient for rate 16/s. `plotMotorDelay.py:32–45` instead uses rate 16 with actual time increments and a different initial state; it contains a plotting comparison, not uncertainty estimation or a held-out lag validation procedure. The paper also acknowledges asymmetric measured lag and transport delays. Do not mistake the chosen scalar rate for verified synchronization or a universal per-motor delay model.

Crucially, `training.py:682–703` merges flights before calling `Fa` at `:719–750`. `utils.py:144–156` creates artificial continuous timestamps at the joins, and the delay recursion has no per-flight reset. Therefore its state carries from one recording into the next. A later reconstruction must preserve run boundaries and prospectively specify initial-state/boundary treatment; the source does not establish that the resulting join transients are harmless.

**7. Holdout and filtering do not establish independent deployment coverage.** `utils.py:414–425` divides the concatenated sequence into 50 contiguous equal-sized blocks after discarding the remainder, fixes a scenario-derived random seed, and selects 10 blocks for validation. This agrees with the paper's block-split description; it is not a random-row split. It is also not a whole-flight, vehicle, day or hardware holdout. Reciprocal receiver records from the same physical flight are assembled into scenario datasets (`training.py:763–772` and later scenarios), with no source group identity enforced by `split`.

Filtering occurs before that split (`training.py:827–830`) and depends partly on the output: `utils.py:266–269` excludes large-magnitude vertical residuals and a subset of large positive residuals, in addition to spatial/ground conditions. This changes the evaluated target distribution. The selected default delay label also has temporal memory across prospective block boundaries; the optional filtered numerical branch uses noncausal `filtfilt` before splitting. Neither observation alone quantifies leakage or invalidates the paper's results, but neither permits treating those validation blocks as independent physical tests. The four-file admission audit should retain complete unfiltered files and report diagnostic flags without making a fitted/scored holdout claim.

## Admission boundary for the next bounded protocol

Proceed only with byte/schema/provenance and complete-record quality observations under the separately frozen four-file protocol: retain public blob IDs and file/vehicle/run association; retain raw clocks and all columns; report missing/nonfinite fields, timestamp cadence/overlap, quaternion conventions and bounds, and calibration-domain flags. Keep every original record and report any prospective exclusion rule separately. None of those observations supplies a force-reference certificate.

Before any later label reconstruction or physical comparison, freeze the target equation and frame/gravity convention, per-run mass/calibration mapping, clock-alignment policy, lag initialization/boundary treatment, quaternion handling, and a whole-run/vehicle holdout policy appropriate to the claim. The original residual target also includes ground effect, drag and other nominal-model errors; it is not automatically identifiable as only the current inter-drone wake contribution. No fit, model score, accuracy claim or novelty conclusion is authorized or established by this review.
