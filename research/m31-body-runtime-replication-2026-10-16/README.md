## What we tried

We asked whether an ordinary binary32 browser calculation could reproduce the assumed model's complete airflow-to-body-load output within fixed tolerances. The planned sequence was small controls followed by four static families, including 5,000 sources. This distinct allocation followed a separately preserved browser-version admission failure. It retained the numerical equations and targets while checking the installed browser before constructing numerical controls.

The actual run reached only the first GPU control dispatch: 15 active records in 64 launched lanes. Its required 3,840-byte output was not persisted. The sink reservation stayed unstarted and incomplete. The GPU scalar controls, returned-value reference, main-family generation and body-output query were not reached. The fixed CPU control inputs and references were retained.

## What improved, and what remains open

The previously blocking runtime identity check now passed for the explicitly pinned Chrome 155.0.8059.80 executable, with a nonfallback Apple / metal-3 adapter. All three pipelines compiled. This is an observed setup outcome, not a causal browser-version comparison or a portability result.

The new failure is evidence persistence. It supplies neither an accuracy pass nor an accuracy counterexample. The records do not establish CORS, a browser-policy change, a driver defect or a sink defect as the cause. We preserve that uncertainty instead of guessing.

The [source-contract planning record](../m31-source-contract-planning-2026-10-16/README.md) identifies a separate physical limitation: the source wake is prescribed from isolated hover rather than calibrated to motor-dependent thrust. Numerical agreement with that model would not resolve this physical question. Independent compatible thrust/flow measurements are still missing.
